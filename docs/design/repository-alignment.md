## Что поддерживает существующая модель

| Элемент интерфейса | Модель/поле | Решение дизайна |
|---|---|---|
| Выбор клиента | client.id, client.name | Клиент в фильтре |
| Имя функции и тариф | faas_function.name, client_id, tariff_id | Тариф показывать у функции; не предполагать один тариф на всех |
| Число вызовов | metric.calls_count | Сумма calls_count, не количество строк metric |
| Длительность и ресурсы | duration_ms, memory_mb | Время и ГБ·с; формулу billed duration подтвердить с backend |
| Холодный запуск | is_cold_start | Признак есть, отдельной init-длительности нет |
| Время и идентификатор события | occurred_at, received_at, event_id | UTC, миллисекунды, копирование ID |

| Состав стоимости | price_per_call, price_per_ms, price_per_gb_second | Отдельные вызовы, время и ресурсы допустимы |

Модели invoice/invoice_item не были показаны в проверенном списке `backend/app/models`; строки таблицы основаны на ERD, а не на подтверждённом работающем API.

## Требования ТЗ, которые ещё требуют согласования

1. В metric нет status/error: долю ошибок нельзя вычислить из показанных полей.
2. Нет init_duration_ms: нельзя восстановить длительность cold start и его ГБ·с из одного boolean.
3. В тарифе не показаны бесплатные лимиты, ступени и шаг округления из раздела 9 ТЗ.
4. Тариф привязан функции, тогда как часть ТЗ описывает тариф клиента. Шапка с одним тарифом допустима только для выбранной функции или одинакового тарифа всех функций.
5. В metric не показана ссылка на версию тарифа; в ERD она есть у строки счёта. Момент определения версии и объяснение события должен дать API.
6. В моделях не показаны хэш, счётчик повторов и сведения об отклонённых событиях. UI для этих требований — целевой, до появления API.
7. Передача memory_mb по умолчанию, описание функции, выдача ключа интеграции и режимы оператора/клиента требуют контракта API: модель функции содержит только id, client_id, tariff_id и name.

## Как читать комплект

- Листы 01–15: целевой дизайн по предоставленному ТЗ, с явно отмеченными демонстрационными данными. Не являются доказательством готовности backend.
- Листы 16–17: вариант интерфейса под уже имеющиеся сущности и поля команды, без выдуманных значений БД.
- Поле price_per_ms не является ошибкой. Ранее прозвучавшее утверждение о безусловной двойной оплате было слишком категоричным. Корректность зависит от модели тарифа: при отдельной ненулевой ставке оплата времени — самостоятельная статья, при нулевой ставке строка имеет нулевое значение/скрывается по согласованному правилу.
- Пример Standard v2 из ТЗ использует вычисления по ГБ·с и включает init в них. Его нельзя автоматически применять к cold_start_surcharge из текущей модели команды без согласования правил.

Окончательный набор правил и дополнительных полей утверждает Team Lead совместно с backend-разработчиком. Дизайн сохраняет оба источника и показывает различия, не меняя работу сокомандников.
